# Place Index — the game's place names are alphabet tiles, not a string table

**Status: built 2026-11-08.** `tools/place_index.py` decodes them; `disasm/place-index.tsv`
is its generated output and is never hand-edited. This page is the interpretation.

> **The finding, in one line.** Ultima II has no place-name string table anywhere — not in
> `ultimaii.exe`, not in `tlkxNN`. The names are **drawn in the world map as tiles, one
> capital letter per cell**, so `mapx22` contains the letters T-O-W-N-E L-I-N-D A as map
> data, and the town's name is recoverable from the sector's bytes without playing the game.
>
> This was the owner's hypothesis, offered against an initial reading that the names were
> third-party wiki invention. The bytes settled it: **the game does name its places, and
> almost every community name checked is the game's own text.** Reported here because the
> wrong reading was held for a whole session and was only displaced by looking at tile bytes
> instead of at strings.

---

## 1. The mapping, and why it is trusted

A map byte is an art index shifted left by two, so `art = byte >> 2`
(`docs/tile-art-evidence.md` A1, measured live on 53 of 54 walk samples).

| art range | letters |
| --- | --- |
| `0x20`–`0x2F` | A–P |
| `0x30` | **not a letter** — a wall tile |
| `0x31`–`0x39` | R–Z |

**There is no Q glyph in the game.** That is not an inference from absence; it is confirmed
by the data using the gap. `mapx93` spells the queen's chamber **`KUEEN`**, because a data
set with no Q has to write it that way. One misspelling, found in a sector nobody had read,
validates the whole table.

The two separators, read off the bytes rather than guessed:

* `0x78` (art `0x1E`) is the **space** tile. In `mapx22` at y=63 the name is stored as
  `TOWNE 0x78 0x70×4 0x78 LINDA`.
* `0x70` (art `0x1C`) is **empty ground** — the most common byte in most sectors.

## 2. The decode rules, stated so they can be argued with

A derived view that hides its rules is a derived view that will be disbelieved later, so
every threshold in the tool is a number with the samples that produced it in a comment.

1. **Word join.** Two letter-runs on the same row are one phrase when the gap between them
   is **≤ 6 cells**. Measured: `TOWNE`→`LINDA` is 6 apart and `THE`→`ARMOURY` is 1 apart,
   while `mapx31` y=0 carries two *different* signs — `THINGS ARE NOT AS THEY SEEM` ending
   at x=27 and `SAIL OUT THE NORTH CHANNEL` starting at x=37 — 9 apart. The threshold sits
   in that gap.
2. **Two-line names.** A bare kind word (`TOWN`, `TOWNE`, `CASTLE`, `TOWER`) with a run
   directly above it overlapping in x is one name split over two rows. `mapx11` writes
   `BARADINS` at y=35 x=28..35 and `TOWN` at y=36 x=30..33. Written as a rule, not a
   special case, because the next stacked two-liner would need a second special case.
3. **Structural fill.** A run of one repeated glyph is structure, not text. The common case
   is `I` (art `0x28`), used as posts and fence lines, which decodes as `I I` once the gap
   rule joins adjacent posts. Dungeons and towers are the extreme case: `mapx15`, `mapx24`,
   `mapx25`, `mapx34`, `mapx35`, `mapx44`, `mapx45`, `mapx85` come out as dozens of rows of
   `AAAA…`, which is the map using a letter index as wall fill. `docs/tile-art-spec.md` § 7
   warned of exactly this — *"in some sectors these same indices are used as structural fill
   rather than as letters"* — and it is the reason a naive decode looks broken.
4. **Name candidate.** A phrase is offered as a *name* when it opens with `TOWNE`/`TOWN`/
   `PORT`/`CASTLE`, closes with `TOWN`, or is the only non-fill run in a settlement sector.
   Everything else is reported as `rooms` — real decoded text, not claimed as a name. The
   column is called **candidate** on purpose; see § 4.

### 3a. Era persistence, which was the owner's point and is now measured

**`mapx23` and `mapx33` have identical decoded text.** Same rooms, same order: `VAULT LORD
BRITISH KITCHEN`, `MESS HALL`, `PRISON`, `THE CHAPEL`. That is Lord British's castle in
1423 B.C. and again in 1990 A.D. — the same place in two eras, which is exactly the
behaviour the owner described: *a player who wants Lord British can get there in any era,
but Port Boniface may only exist in 1990.*

The corollary matters for a bot and for `docs/goal-spec.md`: **place identity is not the
sector number.** Sector 23 and sector 33 are different sectors and the same place. An index
keyed on sector alone would count them as two places and would send a bot to the wrong
conclusion about reachability. The grouping key has to be (name, kind), with era as a
property of the appearance rather than of the place.

And the converse holds too: `PORT BONIFICE` appears only in sector 31, era 3. Some places
are era-bound and some are not, and the index is what tells you which is which.

### 3b. The planets, and their names are in the binary too

The world names are **not** third-party. At file `0x72B9` the executable holds
`YOU ARE ORBITING `, then eight `jz rel8` arms (`0x74` followed by monotonically increasing
offsets `0x23, 0x2D, 0x39, 0x43, 0x4C, 0x58, 0x63, 0x6E`), then nine NUL-terminated names:

```
EARTH.  MERCURY.  VENUS.  MARS.  JUPITER.
SATURN. URANUS.   NEPTUNE. PLUTO.
```

The game prints `YOU ARE ORBITING MERCURY.` by concatenation, so the table order **is** the
world byte's order: `0`–`8` = EARTH … PLUTO, `9` = **X** (printed from a separate routine
past `0x729B`, per `docs/handoff-2026-11-03.md`), `0x0A` = deep space. It sits in the same
code region as the world coordinate table at `0x7212` that the rocket work found, which is a
consistency check in itself.

`tools/place_index.py` reads this table at run time rather than transcribing it, and
`--verify` **fails if the read falls back to the hard-coded list** — otherwise a broken parse
would print the same nine names and look identical.

**Sector 32 is two different places.** Earth-1990 gives New San Antonio; Mars gives Towne
Mary. The filename cannot tell them apart and the world byte can, which is why the index
carries `layer` and `world` columns instead of merging the two sets — collapsing them would
hide the single most interesting fact about the off-Earth data.

`TOWNE MARY` is in the `--verify` controls, so the MAPG layer is guarded and not merely
printed.

**Still unnamed by the game:** the Jupiter village (sector 41) and the Jupiter tower-class
sector (44 or 45). Their decoded text is shop signs or nothing at all.

### 3c. The third-party crosswalk, and what it does and does not prove

Community names now live in `disasm/place-wiki-names.tsv` and land in a **separate `wiki`
column**, never in `candidate`. That separation is the whole design: a reader can always tell
what the bytes said from what a wiki said. `--verify` fails if a crosswalk row names a sector
the tool cannot resolve, so a typo'd sector cannot sit in the table pretending to be a
supported identification. Control exercised: pointing a row at sector 49, which does not
exist, goes red.

Two Jupiter names, and they are worth different amounts.

**Village of the Preppies (sector 41) — corroborated, with a catch.** Our own decode of
`MAPG41` reads `EAT PREPPIES` and `IZOD BURGERS`. So the wiki and the bytes are looking at the
same thing. The catch is what those signs *are*: they are shopfronts, and parodies at that
(*Eat Preppy Foods* is a restaurant chain; Izod is a clothing label), not a title sign for the
settlement. The honest statement is that the wiki name almost certainly **derives from the same
signs we decoded**, which makes it consistent with the data rather than confirmed by it. The
game still does not name this village.

**Jupiter Tower (sector 44 or 45) — unresolvable from the bytes, and said so.** The name is
exactly what our derived tables would predict without any external input: world 4 is JUPITER
(the string table at exe `0x72B9`) and kind 4 is tower (`u2_site_kind`, `asm/343F`). But the
wiki's own entry is ambiguous — it calls it *Jupiter Tower* and describes it as a *dungeon on
Jupiter* — and there are two dungeon-class Jupiter sectors: 44 (kind 4, tower) and 45 (kind 5,
dungeon). **Neither contains a single letter of tile text, and neither has a dialogue file**, so
there is nothing in the data to choose between them. The crosswalk carries 44 as the primary
reading and 45 as `unresolved`, which is the truth rather than a coin flip dressed as a finding.

One incidental fact fell out of checking this: **sector 44 is the only sector in the collision
range whose root `mapx` and patched `MAPG` are byte-identical** (40, 41 and 45 all differ). So
Earth-Aftermath and Jupiter genuinely share that map, which is consistent with it being the one
planet map that was never overwritten because it was never distinct.


## 4. What is still open

* **`candidate` is a claim, not a proof.** The name rules are heuristics over layout. A
  sector could carry its name in a phrase the rules do not match, and `SHADOW GUARD` is
  sitting in the `rooms` column right now as evidence that they can.

* **Sector 32 on Earth has no title sign at all — but the game hard-codes it.** Its decoded
  text is `AIR PORT`, `PRISON`, `ARMOURY`, `SWASHBUCKLERS SWIM AT OWN RISK`, `PUB AND PIZZA`,
  `CUSTOMS`; nothing spells its name. Two independent byte facts now anchor it to the wiki's
  **New San Antonio**: `tlkx32` says `A CLERK STATES: WELCOME TO THE HOTEL CALIFORNIA!` (and the
  game abbreviates the place to `NEW SAN.` in `tlkx82`), and `asm/3C2E_cmd_O.asm` gates its
  entire special-offer path on `DS:4A==2 && DS:49==3` — **sector 32 and nowhere else** — so the
  quicksword, the force field ring and the stat-raising offer all only work there. That is the
  strongest third-party join in the index: the game refuses to name the place, but it will not
  do the quest-critical things anywhere else either. Grade stays `inferred`, because the name is
  still supplied from outside this binary.
* **Sectors with no decoded text at all**: 00, 20, 30, 40, 50, 60, 70, 80, 90 are the
  wilderness sectors, and 10, 44, 45, 15, 24, 25, 34, 35, 85 are towers and dungeons whose
  only "text" is fill. A wilderness sector has no name to find, which is consistent and worth
  stating rather than leaving as a hole.

## 5. Cross-checks that agree

Three independent sources line up on the endgame chain, which is the strongest thing on this
page:

* `mapx93` tiles say **CASTLE BARATARIA**, `KUEEN SUSANS ROOM`, `KING OZYS ROOM`, `JAIL`.
* `tlkx93` (decoded, high bit stripped) says **`FATHER ANTOS CHANTS: YOU HAVE EARNED MY
  BLESSING. RETURN AND CLAIM THE RING!`**
* The third-party walkthrough says Father Antos is in Castle Barataria on Planet X.

Sector 93 is era 9 = world 9 = Planet X, kind 3 = castle. All three agree without any of
them being checked against the others.

`mapx03` naming `CHAMBER ONE` and `CHAMBER TWO` is a second independent hit: the walkthrough
says Minax teleports between a north-east and a south-west chamber, and the map has two
labelled chambers. That is `docs/goal-spec.md` W5/W7 gaining map-level support, and it is
the first in-repo corroboration of the fight's shape.

## 6. Method note

The names were missed because the search was for **strings** and the data is **tiles**. Every
tool in this repo that looks for text — `strings_atlas.py`, the extractor, the CFG printer —
scans for character runs, and a place name stored as one-letter tiles is invisible to all of
them: the bytes are `0xCC 0xB8 0xD8 0xB4 0x90`, which is not ASCII for anything. The fix was
not a better string search but asking what the *renderer* would draw at those cells.

A second, smaller trap: `tlkxNN` dialogue is stored with the high bit set, so a plain ASCII
scan finds nothing and concludes the file has no text. `engine/src/core/world.c`
`u2_world_tlkx_record` already masks `0x7F`; the scan simply had not been pointed at it.
Decoded, `tlkx` turns out to carry the game's only proper nouns (`HOTEL CALIFORNIA`,
`NEW SAN.`, `SAN JOSE`, `PLANET 'X'`) and most of its progression hints.
