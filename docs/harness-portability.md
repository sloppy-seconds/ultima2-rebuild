# Generic DOS decompilation harness — design report

**Status: draft, live document.** Owner-directed 2026-10-22. Purpose: capture what
this project has learned about *method* so a second target — Ultima III, or
another period DOS binary — starts from a harness rather than from scratch.

> **The central tension, stated up front.** Everything here is generalised from
> **n = 1**. A rule derived from one binary is a hypothesis for the second, not a
> law. And the more useful this document gets, the more danger it carries: it must
> transfer *method* without smuggling *conclusions*. A new project that inherits
> this one's addresses has been contaminated, not helped — which is the exact
> failure `AGENTS.md` § 0 exists to prevent. So: **no addresses, no DS layout, no
> symbol names, no game-specific constants in this file.** Examples may name a
> finding to explain a rule; they may not carry the finding's content.

---

## 1. What actually transfers, in three tiers

**Tier 1 — ISA and platform. Transfers to any 16-bit real-mode DOS game.**

* **Packed-decimal arithmetic is a fingerprint.** `adc`/`daa` for add, `sbb`/`das`
  for subtract. Reading the *width* of the byte chain tells you a field's ceiling,
  and the presence or absence of a clamp tells you whether it saturates or wraps.
  This yields whole mechanics from bytes alone, with no play.
* **The borrow-reexposure idiom.** `cmc; sbb; das; cmc` deliberately restores the
  borrow in CF so a following `jb` can branch on it. A guard detector that searches
  for `cmp`/`test` will report every one of these as unguarded. This is a trap for
  tooling, not for humans.
* **Multiple address spaces differing by a constant.** File offset, runtime segment
  offset, and linear address are usually three different numbers for the same byte,
  and mixing them silently finds nothing. Derive the mapping once, verify it against
  one known case, and never hand-add offsets again.
* **Jump-table dispatch hides entry points from static decompilers.** Command
  handlers reached by `jmp *reg` are invisible to Ghidra and Reko. Runtime
  execution traces are the only reliable seed list — and *discovered* blocks are
  not *executed* blocks.
* **Display sites identify fields.** The routine that prints a label and then loads
  a specific memory pair tells you what that pair holds. This is the cheapest
  field-identity oracle available and needs no play.
* **BIOS data area and video-model traps.** Absolute-address arithmetic on the BDA,
  and graphics mode meaning the "text page" holds pixels. Both produce plausible
  garbage rather than errors.

**Tier 2 — method. Transfers to any reverse-engineering effort.**

Evidence grading (`observed` / `measured` / `inferred` / `recalled`); prove-or-pass
rather than guessing; every tool validated against a negative control before its
output is cited; **a gate must be demonstrated to fail before it is trusted to
pass**; derived views generated by tools and never hand-maintained; read a whole
function before describing it; a wrong name is worse than no name; owner
recollection outranks agent inference and is worth measuring even when nothing
contradicts it; bytes outrank everyone, including the owner.

**Tier 3 — does not transfer.** Entry-point lists, segment layouts, record formats,
symbol names, any conclusion about this binary. Regenerate from the new target's
own bytes.

## 2. The play / static split, measured

The owner's question was whether the process is teaching us to derive statically
what we previously needed play to discover. This session's findings, classified by
what actually produced them:

| derivation | findings |
| --- | --- |
| **purely static** — no play, no capture | tool-bug fixes ×3, an addressing anomaly, a data-file decode, the whole decimal-counter census, a repo-invariant rule |
| **play spotted it, bytes explained it** | a currency wrap, a map-vs-file grid discrepancy, a resist probability |
| **static refuted a premise, play confirmed** | a trigger that turned out to be a mode byte, not a tile byte |
| **play-only, still blocked** | a tile→mode mapping, a large byte-space decode, a passability question |

The ratio is already skewed toward static, and it **compounds**: one play-derived
instance, once generalised into a rule, retires a family of future captures. The
clean example is a currency wrap observed once in play, generalised by census into
"every packed-decimal counter wraps at its digit capacity", which then predicted
behaviour for stats and inventory counts that had never been observed — and matched
the owner's recollection, which no agent had thought to test.

**Where play remains irreplaceable.** Three things static analysis cannot do:

1. **Existence.** Bytes contain every mechanic but advertise none. You cannot look
   for a behaviour you have no reason to suspect.
2. **Reachability.** Static analysis proves a code path *exists*; only play proves
   it is *inhabited*. A census can prove a counter has no underflow guard and still
   be unable to say whether the game ever decrements it at zero. **This is the hard
   limit on going static-only: the space of possible behaviours is not the set of
   actual ones.**
3. **Tiebreaking under-determination.** Where a value is produced by an indirect
   write with no static attribution, no amount of reading disambiguates it.

Correct framing: **play is an oracle for where to look and what is reachable;
static analysis is where the knowledge lives.**

## 3. Current toolchain audit

43 Python tools, 8 shell scripts, 4 Ghidra scripts. They split cleanly, and the
split is the design input:

**Already generic — lift almost unchanged.** The proof and verification harness:
per-function byte proof, clean-rebuild byte match, assembler dialect handling,
citation/provenance checking, VGA ink metrics, ring-buffer frame capture. These
carry no knowledge of this game's data layout.

**Game-shaped — encode conclusions inline.** Save/content editors, map and sprite
renderers, the live turn recorder, the decimal census's field table, the emulator
launch script's filename set. Each embeds the field map, the content-file names, or
the segment arithmetic.

**The coupling is worse than the counts suggest.** Tools that take paths as
arguments still embed field offsets as bare numeric literals in slicing expressions,
so a grep for named constants under-counts them. Any port estimate based on visible
constants alone is optimistic.

**A precedent worth generalising.** One tool already does this correctly: it derives
the code segment from where a known routine *executed* rather than hardcoding a
segment value, and fails loudly if that derivation is ambiguous. That pattern —
**derive from evidence, refuse to guess, fail loudly** — is the template for the
whole harness.

## 4. Proposed architecture: generic harness + declarative profile

The blocker to reuse is not that tools are U2-specific; it is that game knowledge is
**fused into tool logic**. One refactor separates them.

```
harness/            generic, no game knowledge
  profile.py        schema + loader + validation
  proof/            byte-match, per-function proof, dialect
  observe/          capture, record, render, diff
  decode/           census, string extraction, classifier
  gates/            the CI checks (each must be shown red once)
profiles/
  <game>.json       ALL game knowledge, declarative, one file per target
```

A new target is "write a profile", not "port a toolchain". Profile contents:

| section | holds |
| --- | --- |
| `artifact` | executable name, content-file globs, save-file name, sidecar data sets |
| `addressing` | file↔runtime↔linear mapping, segment bases, and *derivation rules* where a value is derivable |
| `fields` | offset → name, width, encoding (`bcd`/`int`/`flags`), ceiling, save-record membership |
| `oracles` | display sites that identify fields; known string anchors |
| `seeds` | runtime entry points from execution traces, and how they were obtained |
| `video` | mode, framebuffer model, BDA addresses |
| `turn_model` | turn-based vs realtime, what advances state, food/step economy hooks |
| `invariants` | the byte-match md5, per-checkpoint gate commands, what must never change |

Design rules for the profile:

* **Declarative only.** No logic. If a value is derivable at runtime, derive it and
  record the derivation, not the value — a hardcoded segment or base is a stale
  fact waiting to lie.
* **Validated at load.** Unknown encoding, overlapping fields, or a field outside
  the declared save record are errors, not warnings.
* **The profile is the contamination boundary.** It is the one artefact that may
  hold conclusions, and it is per-target. Nothing generic reads another target's
  profile.
* **Every gate ships with its own negative control**, run in CI, so a gate that
  cannot fail is detected as a failure rather than assumed to be passing.

## 5. The feedback loop (this is the part that has to be enforced)

A design report that is not updated becomes a stale document that argues against
what we now know — the failure mode `AGENTS.md` § 3 already names for hand-kept
indexes. So the obligation is a same-commit rule, recorded in `AGENTS.md`:

> When a finding would change how a *generic* harness should be built, the commit
> that records the finding also adds a line to § 6 of this report.

Candidates are easy to miss because they usually look like a bug fix:

* a tool that returned a plausible wrong answer → a new negative control
* an idiom that broke a detector → a new Tier 1 entry
* a gate that could not fail → a new gate rule
* a class of false positive → a new validation step
* a place where play was the only way to know → a `seeds`/`oracles` profile field

## 6. Feedback log

Newest first. One line per learning; the detail stays in the owning document.
* **2026-11-07 — A verification gate that only ever runs synthetic fixtures will pass
  right up until a real user runs it once.** The record/playback subsystem cleared
  fifteen checks with their red controls and then failed on the owner's first real
  recording, in three separate ways that no fixture could reach. (1) The fixture's world
  was pristine, so it never exercised the case where the recorder reads a sector from its
  own save overlay while the viewer, correctly isolated from that save, reads the content
  copy — two honest runs, different layers, a false refusal. (2) Every fixture stopped
  the recording with the toggle, so the quit-stops-the-recording path — the one the
  request actually named — had never been compared at all, and its closing digest was
  being checked at the wrong instant. (3) Every fixture entered the world by a dev flag,
  so the ordinary route through the menu was never walked. Transferable rule: for any
  record/replay feature, the first thing after the synthetic gate goes green is one
  recording made the way a person makes one, on a tree with real saves and real content
  layers, and that run belongs in the gate rather than in a demo.
* **2026-11-07 — A refusal needs an explicit human override, or the refusal becomes the
  bug.** Content-digest mismatches refuse to play, which is correct as a default and
  immediately strands any recording whose content cannot be reproduced — including
  recordings the previous build made before the layer distinction existed. The shape that
  works is the one already used for truncated files: refuse by default, one flag to
  proceed, and the run states on the way in that the override was used and what it may
  cost. Two transferable points. (1) When you add a refusal, name the situation in which a
  person will legitimately want to walk past it, and give them a door before the first
  user finds the wall. (2) A superseded build can leave artefacts that a later, stricter
  check rejects; "re-record it" is not a fix when the artefact is the evidence someone
  wanted to look at.
* **2026-11-07 — A replay verifier must hash the state at the same point in the loop
  on both sides, and "the same loop iteration" is not the same point.** A record
  written before a key is delivered holds the state *before* that key, so the only
  comparison that can succeed is that record against the live state at the same
  boundary — not against the state after the key, which is what "verify the previous
  record before delivering the next one" reads like and what the first implementation
  did. Two transferable points. (1) Where a record's digest is taken relative to the
  frame draw decides the verdict: a closing digest captured after the draw on one side
  and before it on the other differs by exactly one frame's worth of cursor movement,
  and that looks like an engine bug rather than a pairing bug. Pin the pairing in
  prose next to the code that computes it, because nothing in the types says which
  instant was meant. (2) The last record has no successor to trigger its check, so the
  format needs a closing digest and the verifier needs a place to compare it that is
  the same instant the recorder wrote it. A run that ends before that point must fail
  with a name — "the closing state was never reached" — rather than pass.
* **2026-11-07 — A recording facility must never write to the surface its own digest
  covers, and the announcement the player needs has to go somewhere else.** If the
  per-record digest includes the screen, then a "RECORDING" banner printed to the game
  screen is present in the recording and absent from the playback, and the first record
  mismatches for a reason the engine caused. Two transferable points. (1) Route
  recorder and player notices to a channel the digest does not read — the same channel
  the screenshot key already uses — and say why in a comment at the print site, or the
  next person will "improve" the UX by moving the message onto the screen and break
  verification. (2) The same asymmetry bites anywhere the observer writes to what it
  observes: a checkpoint that restores state but not the screen cannot vouch for the
  screen, so either carry the screen in the checkpoint or keep it out of the digest,
  and say in the header which one you chose and what that makes undetectable.
* **2026-11-07 — "Record the input the game consumed" needs a seam that every mode
  passes through, and a toggle that arms itself at the seam.** Logging raw keystrokes
  records input the game never read; logging resolved actions needs a hook in every
  handler. Tapping the one place a key becomes game logic gets both right, but only if
  the first press of the toggle can arm the recorder from there: a toggle handler that
  returns "no key" and waits for the next quiescent point loses the key that arrives
  in between, because the seam fetches a replacement inside the same blocking call.
  Two transferable points. (1) Distinguish "a boundary is open right now" from "a
  boundary will come", and honour the toggle immediately when the caller is already
  standing at one. (2) The quiescence rule still has to hold mid-command, so the flag
  needs clearing when a key goes out — otherwise a press during a half-typed command
  takes effect in the middle of it.
* **2026-11-07 — A checkpoint can only resume a mode whose position lives in the state
  the checkpoint carries.** Recording was refused in two modes after measurement, for
  two different reasons, and both are the same rule. The title screen reaches its menu
  by consuming keys of its own, so a checkpoint there cannot be resumed without
  replaying input the recording never made. A character-creation form keeps its cursor
  — which field is highlighted, which dropdown is open — in a local struct, so a
  checkpoint taken mid-form names a state playback cannot resume and the digests
  diverge a few keys in. Two transferable points. (1) Before building record/playback,
  enumerate the per-mode scratch held outside the mirrored state and refuse to record
  where it matters; a refusal that names the reason is worth more than a demo that
  replays wrong and looks like an engine defect. (2) "Quiescent" is not one condition
  but one per mode, and the honest set is the modes with no such scratch at all.
* **2026-11-07 — An argparse `REMAINDER` positional swallows the options declared
  before it, so a pass-through-to-subprocess flag must be `append`, not `REMAINDER`.**
  A wrapper that forwards extra arguments to the binary it drives was written as
  `extra: REMAINDER` after `--engine` and `--data-dir`; parsing
  `--engine X --data-dir Y -- --flag` put all four tokens in `extra` and left the real
  options at their defaults, so the subprocess was launched with the wrapper's own
  option names and failed with a usage dump the wrapper reported as a bare exit code.
  Two transferable points. (1) Use a repeatable `--engine-arg` for pass-through and
  document that its value must be one token (`--engine-arg=--flag`). (2) When a wrapper
  reports a child's failure, carry the child's own diagnostic line into the verdict;
  "exit 2" tells a person nothing about which file or why.

* **2026-11-05 — A "nothing changed" gate must also prove that something was written,
  or it passes on a run that did nothing at all.** The property worth gating in any
  reconstruction that plays against player-supplied content is *the content tree is
  immutable while the game runs*: hash every file under the content root, drive a
  scripted session, hash again, require zero differences. Two transferable points.
  (1) That assertion is vacuous in exactly the case that matters — a session that never
  reached a write — so the gate must assert the positive half in the same run: the
  overlay the writes were supposed to produce has to exist, and be the file that
  carries the change. A green hash comparison with no overlay behind it is a gate that
  checked nothing. (2) Give the comparison its own red control and run the control on
  every invocation rather than on demand: dirty one byte of the tree between the two
  hashes and require the diff to name it. Then demonstrate the whole gate red in the
  position it enforces, by building the engine against the write rule it replaced.
  Both halves together are what distinguish a gate from a ceremony.
* **2026-11-05 — To force a write failure in a test, chmod the file, not its directory.**
  A gate meant to prove "a save that cannot be written says so" made the save directory
  read-only and the record still wrote fine, because rewriting a file in place needs write
  permission on the *file*, while creating, unlinking or renaming a name needs it on the
  *directory*. Two transferable points. (1) A write path that stages through a temp file
  plus rename and a write path that truncates in place fail under different permissions, so
  a fixture that chmods one directory can silently cover only one of them -- exercise each
  write path against the permission it actually depends on, and assert them as separate
  cases. (2) The same trap makes a negative assertion pass for the wrong reason: if the
  screen already carries the message from an earlier case, "the refusal was printed" is
  vacuous. Order the cases so the first one to assert a message is the first one that could
  have produced it, or clear the surface between them -- and check that clearing it does not
  change how the surface renders, which it did here and turned a passing positive assertion
  into a column of single characters.
* **2026-11-05 — A layout change that moves a file into a directory of the same name
  cannot be staged, and a harness that assumed one directory level breaks silently in
  teardown.** Moving a save record from `dir/NAME` to `dir/NAME/NAME` (the record and
  its container sharing a name is deliberate, and matches the name the original asks
  DOS for) means the old file and the new directory cannot coexist, so the write-target
  change and the record-path change are one commit or neither: with the flat file still
  present, every write into the directory fails, and the failure surfaces as a game that
  reports "drive not ready" rather than as a build error. Two transferable points.
  (1) When planning incremental steps, check whether step N+1's destination path is
  already occupied by step N's source — an ordering that looks reversible on paper may
  be a name collision. (2) Teardown and verification code that walks a save directory
  with a fixed depth (`for f in listdir(d): unlink(f)`) raises or skips once the depth
  changes; recurse, and let the harness pass an explicit scratch directory so a
  recorded artefact cannot depend on whatever a previous run left in a default path.

* **2026-11-05 — A comparison loop that tests for a file's existence case-sensitively will
  report a confident, plausible, wrong count when the two layers spell names differently.**
  Diffing a base release against a community patch directory, a shell loop skipped every file
  whose case differed, because the existence test silently failed and `continue`d. It reported
  two differing files where the true number was eleven, and nothing about its output looked
  broken. Two transferable points. (1) When comparing two directory trees that came from
  different ecosystems, case-fold the names *before* the existence test, not after, and assert
  that the shared-name count is what you expect -- a loop that silently drops inputs is the
  same defect class as a script slicing from the wrong base offset. (2) On a case-sensitive
  filesystem the two spellings are two files, so any installer or packer that copies both
  leaves both present and lets the consumer pick which one it finds. A derived view over
  legacy DOS media should key on the case-folded name and emit one file, keeping one layer's
  spelling as the visible name.
* **2026-11-04 — When a data sidecar's format is undetermined, look for the program that ships
  beside it which reads it, before guessing at the bytes.** A colour-table sidecar in a fan
  art pack was 32 bytes for what looked like 16 colours, and every in-memory reading of it
  (RGB555, nibble pairs, an index remap) was a guess that a byte-level check could not refute.
  The pack also shipped the real-mode driver that opens the file, and that driver settled it in
  a dozen instructions: a fixed-size whole-file read over a built-in default table, then five
  indexed reads whose values go to the pixel and character-attribute writers, and a blit path
  that never consults the table at all. Three transferable points. (1) A third-party pack is
  usually self-consistent: if it ships a loader, patcher or driver alongside the data, that
  binary is the format spec and it is static, so the decode costs a disassembly and not a
  capture. (2) A fixed-size read (`mov cx,N; rep movsb`) is a size contract, and the presence
  of a built-in default of the same shape in the reader's own data area is stronger evidence of
  the record width than anything derivable from the file. (3) Distinguish a palette from a
  remap by *where the value goes*: a value written to a palette register is a colour, a value
  written as a pixel or attribute index is a remap, and the two need different engine
  mechanisms even when they look like the same 32 bytes.

* **2026-11-02 — A measurement taken where two hypotheses look identical cannot decide between them,
  however carefully it is taken, and the reconstruction will generalise the result to every case that
  was never tested.** A viewport rule was established from a live capture and then applied to every
  sector class. It was right for the class that was captured and wrong for the others, and it sat in
  the code with a citation, which is the reason nobody re-tested it. The capture was not sloppy: the
  sector used has the same tile at both of the edges the rule concerns, so wrapping and not-wrapping
  render pixel-identically there. No amount of care at that boundary could have separated the two
  hypotheses, and only a sector whose opposite edge carries distinctive content can. Three rules. (1)
  Before citing a boundary measurement as the basis for a rule, ask what the measurement would look
  like if the opposite rule were true — if the answer is "the same", the capture is not evidence for
  the rule, it is evidence that the rule is untestable at that spot, and the work is to find the
  sector class where the two differ. (2) When a rule is derived from a container's class rather than
  from the container, enumerate the classes and say which were measured; a reconstruction that
  applies one class's arithmetic everywhere is making a claim about the classes it never opened.
  (3) A named routine in the reconstruction that branches on a mode byte and takes two near-identical
  arms is a standing warning: the difference between the arms is usually the thing a later
  generalisation throws away, and reading both arms before writing the rule is cheaper than one
  owner-reported bug. → Tier 1, evidence discipline; and the standing rule that a capture earns its
  citation only if it could have failed to.

* **2026-11-02 — A gate that inspects the build's inputs is not a gate on the artifact's
  capability, and a dependency that degrades silently turns a green pipeline into a lie.** The
  shipped single-file Linux player binary had **no display backend whatsoever**: the third-party
  media library's build system compiles out any platform backend whose headers are absent and
  reports nothing when it does, and neither the build container nor CI installed a single one.
  So the artifact contained only the headless drivers. Every check passed — the link was genuinely
  static, the checksum matched, and the pixel-path gate ran under a null video driver and produced
  a correct frame, which proves the render chain and says nothing about whether a window can exist.
  Three rules. (1) When a dependency silently narrows itself, configure it loudly (install the
  headers) and then **ask the artifact what it can do** — one diagnostic flag that enumerates
  compiled-in backends, needs no display, and is greppable by CI, converts a class of silent
  degradation into a red build. (2) A headless test standing in for a graphical one proves the
  layer below the display, not the display; do not let its green mean more than that. (3) When a
  failure is reported by a human as "nothing appeared", treat it as missing diagnostics first: the
  fix is usually to make the program name the thing it could not do, which is what the same flag
  now prints on startup and on failure. → Tier 2, build/gate design; and the standing rule that a
  capability you never asked the artifact about is a capability you do not have.

* **2026-11-02 — A required gate that cannot run in the workflow that runs it is the same defect
  as a gate that cannot fail, and a cross-build nobody but a runner ever links is a rumour.** Two
  halves, both found by cutting a throwaway release tag instead of trusting local builds. First,
  a staleness check was declared *required* with a built binary as its prerequisite, in the one
  workflow that has no build step — so it had been red for days, and a permanent red is
  indistinguishable from noise and trains everyone to skip the suite. A gate needs a home where it
  can both pass and fail; if the only place it can run lacks its inputs, declare it optional there
  and add it to the workflow that has them. Second, the platform cross-build had never linked on
  CI, and never would have: the toolchain *declares* the POSIX time functions and its C runtime
  does not provide them, so the failure lands at link rather than compile and every host that did
  not cross-build saw a clean build. The fix is a real per-platform backend behind the seam that
  already existed, not an `#ifdef` in the portable file. And the honest residue: the new backend
  links, imports only system libraries, and has never executed — no emulator, no runner. Say that
  in the same place that says it builds, or the next person will read "builds" as "works".
  → Tier 2, gate design; and Tier 1 for "the verification you never run is the one that is
  lying".

* **2026-11-02 — A generator with a lossy fallback must not be runnable by the build, and the
  fallback must be demoted to verifier.** The content header for the reimplementation had two
  sources: the shipped binary, which resolves every string, and the reconstructed asm listing,
  which resolves about eighty per cent of them and yields an empty literal for the rest — because
  a bulk wave that renders a span as byte lists or as mis-decoded instructions leaves no quoted
  text for a locator to match. Every developer machine had the binary, so nobody noticed that CI,
  and therefore every artefact CI shipped, silently took the lossy path. The defect is not the
  gap, it is that an empty literal is a **value**: the program runs, the screen renders, and every
  assertion that greps output for the missing text passes while nothing was printed. Three rules
  generalise. (1) Where one source is provably lossy, the build gets no rule to select it — the
  generated file is either committed or the build fails for want of it, and the lossy path is
  refused by the tool rather than by a wrapper, so it holds however the tool is invoked. (2)
  When you demote the lossy source to a cross-check, do not make it cross-check with the same
  weak reader it failed with. The first version inherited the builder's quoted-literal index and
  could only compare 82 per cent; reading the source's whole data payload instead — quoted text,
  bare byte lists, and lines that mix them — proved 97 per cent, and the strings it still could
  not reach were then nameable as a list that only ever shrinks. (3) A fudge in a check is a
  diagnosis. That first version needed "compare only as far as the weaker source can see" to pass;
  once the reader was replaced the allowance was unnecessary, and an allowance nobody needs is
  usually hiding the thing that should be fixed. If a cross-check needs to be told how little to
  look at, look at the reader. Then demonstrate the gate red on each shape of drift (wrong text,
  blanked item, shortened prefix, missing item, attempted downgrade), and make an unprovable item
  a named list rather than a tolerated count, so a new one is a red and a resolved one is a
  message. → Tier 2, gate design; and an argument for treating "the fallback still builds" as a
  defect report rather than a success.

* **2026-10-29 — "No pixel-plot path anywhere in the tree" is a statement about the names, not
  about the code, and it can sit on an item for weeks and make it look owner-blocked.** A whole
  first-person renderer was undiscovered because the search was for a routine that writes to a
  known framebuffer address, and the routine does not: it takes a row SEGMENT from a table
  indexed by y, takes a bit mask from a second table indexed by the low two bits of x, and ORs
  the mask at the pair. Nothing in it mentions a constant that a grep would find. Two general
  rules fall out. First, find a primitive by its **memory-access shape** (table-of-segments plus
  mask-OR is a 2bpp planar plot on any x86 target of the era), not by its destination address or
  a guessed name. Second, treat "the capability does not exist" as unproven until someone has
  looked at every unnamed fragment in the address neighbourhood of the code that would need it —
  here, a run of twelve small routines that all called the same one, which is a drawing library
  by any description even though every one of them was filed as `sub_xxxx`.

* **2026-10-29 — A bulk wave that gives up on a span and renders it as data can bury an entire
  command set in the same way a function-map boundary buries a call, and the tell is the same: a
  header that is accurate about its range and useless about its content.** One region of a few
  hundred bytes was recorded as "dominated by mis-decoded data (all forced-kept bytes) — NOT
  named", and it held four movement commands, a trap, and the two turn routines that pinned down
  what the facing bytes meant. The bytes were all present the whole time. The general fix is a

  an idle tick spent 10 and an action spent 19, so any delta of 9 mod 10 was exactly one action
  however many ticks fired in the gap — that arithmetic made a measurement safe that no amount of
  tightening the timing window would have made safe. And **a byte forced into a live process is
  volatile**: the program restored the mode byte being poked between the write and the input that
  was supposed to exercise it, the poke tool's own read-back said the write had landed, and the
  resulting sample measured the wrong branch while looking clean. Confirm a forced value at the
  moment of the input, in the same read as the thing being measured.
* **2026-10-28f** — **Never let a gate read a hand-kept copy of a fact it could derive.** The
  harness had a crosswalk tool that reported whether each command handler had ever executed by
  parsing a provenance comment in that handler's own file. The comment was written when the capture
  corpus was a certain size, the corpus grew by more than half, and nobody regenerated the comments.
  Eight of twenty-six grades were therefore wrong, including one handler whose evidence was cited in
  an older prose format the parser could not see -- so it reported "never executed" for a routine
  that a quarter of the corpus contained. Every downstream gate did its job correctly on stale input,
  which is the worst possible failure: no error, no red, and a scope ruling was made on the bad
  number. The general shape to avoid is any checker whose input is a human-maintained summary of
  data the harness already holds; the fix is to point the checker at the primary evidence and keep
  the comment as prose context only. Two corollaries the same session produced: a literal count
  baked into a tool's output text ("of the 60 harvests") reads exactly like a measurement and will
  silently age, and a search that misses because of a morphological variant (singular versus plural)
  must be reported as "not found by this query" rather than "absent from the binary" -- the first
  of those cost a false conclusion about an item requirement in the same hour.

* **2026-10-28e** — **Accept a decode proposal by re-assembly, never by a disassembler's
  opinion.** A span the clean wave had rendered as raw bytes was turned back into mnemonics by
  asking a disassembler what the bytes meant and then asking the assembler to reproduce them at
  the same address, with branch-target labels defined at their targets: only a byte-for-byte
  match is emitted, and everything else stays a raw-byte line naming what the assembler was
  asked for. That single rule is what makes the tool safe to run at all — a wrong proposal is
  indistinguishable from a dialect difference otherwise, and the tree already contains hundreds
  of genuine dialect cases where the same instruction has two legal encodings. Two details cost
  real time and both are now controls: an assembler directive that cannot seek backwards will
  silently place the instruction at its branch target and make every forward branch look like a
  dialect problem, and a disassembler handed a very short buffer prints a placeholder instead of
  decoding, which under-claims silently. And the tool prints a candidate and writes nothing, because
  for spans that are unreachable and decode absurdly, a generated mnemonic is a confident wrong
  answer — the review step is the difference between a re-cut and a regression.

* **2026-10-28e** — **A content-conservation gate that compares the working tree to a commit
  cannot see a rename, and a rename is a first-class operation in this pipeline.** The guard
  required an unchanged canonical stream across every non-comment line, and permitted a changed
  stream only inside a file carrying a correction marker. Renaming a file while correcting its
  body — which is what the naming rule demands, since a discovered name belongs in the filename
  in the same commit that learns it — registered as a permitted new file plus an unpermitted
  removed file, and because the comparison was against HEAD the whole pair went green the moment
  it was committed. Two sessions did this before anything caught it. Rule: if a gate permits
  renames as an operation, it must match removals to additions by identity (an address prefix,
  here) and require the attribution on the added side; and it must be run *before* committing,
  because a gate whose verdict changes on commit is measuring the workflow rather than the tree.

* **2026-10-28e** — **A call or jump target is an instruction boundary, and that is a cheap
  proof a linear decode does not have.** Two spans in this tree were held open by a claimed
  instruction straddling into the next fragment, and in both cases the target fragment was the
  destination of a `call` or `jmp` from elsewhere in the binary — which makes the straddle
  impossible without breaking every caller. The spans turned out to be data. Rule for a
  harness: before believing a truncation at a fragment's left edge, look up whether that address
  is a branch target anywhere in the image; it is a whole-image fact that a per-fragment decode
  cannot see, and it costs one index lookup.

* **2026-10-28e** — **A decode tool's error text describes what it tried to do, not what went
  wrong, and a harness that classifies findings by that text will mis-plan the work.** Every
  truncated instruction in this project's reconstruction carried a marker blaming the assembler
  ("the assembler re-encodes this differently"). Re-asking the assembler at the real address,
  with the real context, showed the majority of those markers are false: the assembler encodes
  the instruction byte-for-byte and was only refusing because the fragment ended mid-instruction.
  The cause was the function-boundary detector all along, and the two marker wordings that
  looked like two kinds of fix were one kind of fix. Rule for a harness: where a tool records
  *why* it gave up, re-derive the cause from the bytes rather than grouping on the message, and
  make the re-derivation a mode of the tool so the number is reproducible instead of a claim.

* **2026-10-28e** — **A control that can only pass while the defect exists is not a control, it
  is a second copy of the defect.** A string atlas carried a selftest assertion that its
  fallback source must contribute rows, written when nine messages needed rescuing. Fixing the
  last one made the assertion fail, so the harness reported itself broken for succeeding, and
  the honest-looking response would have been to leave nine messages unfixed. Rule: assert the
  *mechanism* (feed the fallback path something the primary path also sees, and require it to
  agree) rather than the *symptom* (a non-zero count of the thing you intend to eliminate).

* **2026-10-28e** — **A verification script's exit status is part of its output, and mutation
  harnesses get this wrong in three ways at once.** Two mutation harnesses — break one clause of
  a model, require the test to go red — ended on a shell idiom whose last command was `echo`, so
  they exited 0 while printing FAIL; one of them also `cd`'d to a hardcoded absolute path, so on
  any other checkout it tested a different tree, and on a runner the `cd` failed and it tested
  nothing; and one treated "the mutant would not compile" as a skip that was not tallied, so an
  unbuilt tree produced zero mutants and a PASS. Rule: a harness that reports a verdict must
  exit non-zero on it, must count "checked nothing" as a failure rather than a skip, and must
  resolve its own paths; and the control that proves it can go red has to be run from the same
  directory and ref position CI will use.

* **2026-10-28d** — **A second implementation of the same logic in a different ISA is a
  tiebreaker for static ambiguity, and it must be built as a gated lookup rather than a
  reading habit.** Where a port and its ancestor share a string verbatim, the routines around
  the string are the same routine, and a question that cannot be settled statically on one side
  often can be on the other: which of two readings of a compare is right, whether a table is
  what we think, whether a branch is a guard or a fallback. None of that touches execution,
  which stays a play question on both sides. Three method rules, all paid for. **Anchor on
  text, and gate the matcher with a string known to exist on only one side** — the negative
  control is what makes "matched" mean something, and a matcher that reports the platform-only
  string as matched is broken in a way that looks like success. **Require order preservation
  per cluster, not set membership** — strings that cluster into the same tables in the same
  order on both sides is the evidence that this is a translation and not a rewrite, and it is
  computable, whereas a remembered count of "the anchor set" is not (the remembered count here
  was off by a third and nobody noticed until a tool measured it). **Expect the yield to be
  small and say so** — a few percent of the string inventory is a normal honest result, and a
  tool that reports a suspiciously high rate is matching noise.

* **2026-10-28d** — **A cross-ISA corroborator can agree with a wrong reading, and the place
  it agrees is exactly where the ISAs differ.** A port translated a source-side `SEC` before
  `SBC` into a target-side carry-set before a subtract. On the source ISA the flag set is
  *required* for a plain subtract; on the target ISA it does nothing. So a reader who wrongly
  believed the target subtract consumed the carry would find the source code "consistent" with
  the wrong reading — the ancestor implementation would have endorsed a false claim rather than
  contradicting it. The rule for a harness that ships a crosswalk: a second implementation
  raises a claim from *inferred* to *corroborated* and no further, and any claim that rests on
  an instruction-level semantic still needs that semantic cited or measured on the ISA that
  executes it. Corroboration is agreement between two readings, not proof of either.

* **2026-10-28d** — **An extractor whose not-found path is a silent `continue` will lose data
  in a way its own selftest cannot see, if the lost case is positional rather than semantic.**
  A string atlas located each embedded string by subtracting its byte count from the address of
  the next label in the listing, and skipped any string with no label after it. That is not a
  corner case, it is every file whose last emitted line is the string — a fifth of the tree,
  including a string the project used as a negative control elsewhere. The tool reported a
  clean count, its controls passed, and `N/N offsets verify` was true of the strings it chose
  to report. Two rules. Any locator rule needs its **failure mode named in the docstring with
  the shape of input that triggers it**, and a control case must be routed through the rare
  path, not only the common one — a control that passes on the easy case certifies nothing about
  the branch that drops data. Prefer a fallback that can only be accepted by verification (search
  the binary for the exact bytes, accept a unique hit, otherwise drop) over one that guesses.

* **2026-10-28c** — **A flag semantic asserted from recall rather than looked up will produce a
  confident, tidy, wrong finding, and it will survive into a contract if it explains something.
  Check the semantic, or better, measure the value.** A reconstruction read two instructions
  correctly — a carry-set immediately before a subtract — combined them with a remembered rule
  about the carry flag, and concluded the routine computed `a - b - 1`. The remembered rule was
  false: on x86 `SUB` ignores CF and only `SBB` consumes it. Nothing about the byte reading was
  wrong, which is what made it dangerous. The derived claim was behavioural (creatures should
  stall one cell short when approaching from one side), it fitted an unmeasured gap, and it went
  into a written contract before anyone ran it. Two rules for a generic harness. First, any
  decode that depends on a flag semantic needs the semantic cited or checked, not recalled —
  carry behaviour across `CLC`/`STC`/`CMC`/`SUB`/`SBB`/`ADC` is exactly the family where a
  half-remembered rule reads as a bug in the target. Second, and this is the one that actually
  paid: **prefer measuring the value to deriving it.** The claim died in one afternoon by reading
  the two result bytes out of live memory after each turn, twenty trials with a control — which
  is cheaper than the argument that produced it. A derived claim that explains an unmeasured
  behaviour is a prediction waiting to be run, not a finding.

* **2026-10-28c** — **A predicate can return its verdict in the flags, not the return value, and
  a decompiler will report it as a function that always succeeds.** A gate routine ended both of
  its exits with an explicit compare against zero immediately before `RET`, and every caller
  branched on the resulting zero flag rather than testing the returned byte. Read as a value
  the function looks like it returns 0 or 255 and the callers look like they forgot to check.
  Two rules. When a caller branches on a flag right after a call, look inside the callee for a
  `CMP`/`TEST` on its return path and record the convention in the header, because it is a
  calling convention and not a local detail. And prefer to reconstruct such a routine as one
  function with two exits rather than as the fragments the boundary detector produced — the
  verdict polarity is only legible when both exits are in scope at once.

* **2026-10-28b** — **An instruction file that states an environment absolute will be quoted
  as evidence by the next agent, so a stale one is worse than a missing one.** A top-level
  rules file asserted "no display and no Xvfb, so keystrokes are unavailable". The host half
  was still true; the conclusion had been false for many commits, and the same file contradicted
  itself twenty lines later by documenting the key-injection tool. An agent read the summary
  line, quoted it, and used it to rule a whole subsystem out of scope — the failure was quoting
  the rule instead of checking the tool index. Two rules for a generic harness. Environment
  facts live **next to the tool that makes them true**, in one place, and the top-level file
  points there instead of restating them. And any absolute of the form "X is unavailable" needs
  a date and a named probe beside it, because the only thing worse than an environment you do
  not understand is one you misunderstand with confidence. Audit these on the day a tool lands,
  not on request: the drift is invisible from inside the session that causes it.

* **2026-10-28b** — **Never hand-derive a container's sector or block order when a reference
  implementation exists; a wrong skew shifts every record by one and every field still looks
  plausible.** A raw disk image was read linearly, the fixed-size directory records fell out of
  phase at sector boundaries, and the repair attempt produced a grid that parsed cleanly and
  attributed each record's length and load address to the *neighbouring* file. Nothing
  complained: sizes were sane, names were sane, and the error was invisible until an independent
  tool reported the real lengths and every derived number was wrong at once. Two rules for a
  generic harness. First, treat an on-disk container format as a solved problem and vendor a
  real parser as infrastructure, then validate any in-house reader against its output rather
  than against the raw bytes. Second, when checking a structural parse, assert on a field that
  is externally verifiable (declared length, record count, a value the format restates
  elsewhere), not on plausibility of the decoded numbers — a misaligned record yields
  individually plausible numbers far more often than nonsense.

* **2026-10-28b** — **When two loops share a body, check which one the gate belongs to before
  attaching it to the reconstruction.** A per-entity sweep can be entered from more than one
  dispatch site, and a filter that is real in one entry path is absent in another; applying it
  everywhere produces behaviour that looks like a rate limit or a probability and is actually a
  missing code path. The tell is a measured "most of the time nothing happens" statistic that
  has no explicit gate behind it — re-derive the dispatch table above the loop, not just the
  loop, and let the entry sites, not the shared body, decide which filters apply.
* **2026-10-28b** — **A sentinel byte written into the wrong address space survives forever and
  renders as content.** A kill marker copied from a half-read write site landed in the grid the
  renderer indexes, where the index transform turned it into a visible glyph, and the rebuild
  pass was then taught to skip that value so it could not clean itself up. When a constant comes
  from a site whose base register was assumed, verify the buffer by its size and its consumer
  before writing it into a derived view, and never add a skip to a rebuild loop to preserve a
  byte whose address was inferred.
* **2026-10-28b** — **A wrapper named from an INT call shape must have its register split
  decoded first.** A naming wave that labels system wrappers by recognizable INT/port shapes
  read `mov $0x1,%ax` before an `int 10h` as "function 1", but the immediate loads AX: AH is 0
  and AL is 1, i.e. set-video-mode with mode 1 — not the cursor-shape or teletype call the
  label claimed. The wrong name then propagated into the reimplementation's seam map and
  became load-bearing there. Rule for a generic harness: derive the function number from AH
  (or AH and AL separately, when the call takes a pair) after tracking writes to the whole
  register, and refuse to name a wrapper when the write that set the number is not visible
  inside the function's own bytes.
* **2026-10-28** — **If the input of the thing you are measuring can be written, write it; 
  waiting for the program to produce the value is the expensive way to sample a rare branch.**
  A selector that had resisted two sessions of passive trapping resolved in one afternoon once
  the harness could poke the counter and drive one command per sample. The generic shape is
  force input, trigger one iteration, observe. It also converts "we never saw it happen" into
  a real refutation, because the value under test is no longer left to chance.
* **2026-10-28** — **Break inside the branch you are testing, not at the end of it.** Stopping
  at the point where a routine's side effects are already visible means the stop only happens
  when every later guard also passes, so the sample rate collapses and a null result is
  ambiguous between "the branch never ran" and "the branch ran and bailed out". Stopping at
  the branch entry fires regardless, and the registers there usually still carry the value the
  guard is about to test — strictly more information per stop.
* **2026-10-28** — **A breakpoint that cannot be removed and outlives its client is a hazard,
  not a feature.** A multi-shot trap left armed by a finished probe keeps firing, and with no
  listener to resume it the guest halts silently mid-experiment; re-arming the same address
  stacks duplicates and later arming calls start failing outright. A harness should either
  own the trap set for the life of the run or restart the emulator between probe groups,
  and should treat "arm failed" as a state problem rather than retrying the same command.
* **2026-10-28** — **A prompt that reads a key with a bounded poll is a race the driver can
  lose invisibly.** Text adventures of this era print a prompt, poll the keyboard until a
  counter wraps, and then emit a fallback message and leave the state at zero — so a driver
  that sends the prompt key and the answer key as two separate operations with a human-scale
  gap gets the fallback and an error message that blames something else entirely. Send
  prompt-and-answer as one timed burst, and read state, not the screen, to decide whether the
  interaction took.
* **2026-10-28** — **Attaching a remote-debug client halts the emulated guest, and it stays
  halted after the client disconnects.** The status endpoint then reports the CPU as running
  while the cycle counter does not move, and every input sent afterwards is swallowed — so a
  frozen run is indistinguishable from an idle one from the outside. Any harness that opens a
  debug socket must resume the target before closing it, including on its timeout and error
  paths, and should treat "status says running, cycles do not advance" as a named failure mode
  rather than a mystery.
* **2026-10-28** — **On a halted target a debugger-monitor reply can lag the command that
  caused it, so replies must be attributed by content, not by send order.** Sending one
  command and reading one reply produced a packet belonging to an earlier command, which
  decoded cleanly and looked like evidence: a register dump came back labelled as a call
  stack. The durable shape is to send the whole batch, then read until every expected reply has
  arrived, classifying each packet by a signature of what it contains. A protocol that never
  sends a terminator for a reply makes the wrong version look completely normal.
* **2026-10-28** — **A probe whose answer key is a return address has no answer key on
  jump-dispatched code, and it fails by returning a plausible zero.** Hand-written and
  ported 8-bit-era binaries routinely reach deep regions by fall-through and computed jumps
  rather than calls, so the guest stack is empty at the breakpoint and "who called this"
  comes back as segment-zero — a value that parses fine. The harness should read the raw word
  at the stack pointer alongside the emulator's own answer, print both, and say whether they
  agree; and when neither does, fall back to static reachability (who branches into this
  region at all) instead of repeating the capture.
* **2026-10-28** — **An emulator that can add a breakpoint but not remove one makes
  self-tests destructive, and "multi-shot" has to be measured, not assumed.** A trap armed by
  a positive control stays armed for the life of the run and re-fires after every resume, so
  any later capture on that run is stolen by it. A harness whose selftest arms on a live
  address must either restart the run afterwards or arm on an address that can only be reached
  once — and the one-shot-versus-multi-shot behaviour is worth a timed test, because the
  capture workflow differs completely depending on the answer.

* **2026-10-23** — **A vendored, self-contained emulator build is containerisable, but three
  of its assumptions are about the machine that built it, not the game.** Containerising the
  emulator for a browser-watched play session surfaced all three, and each failed as something
  else: (1) the apphost's `PT_INTERP` is the build machine's loader path, so the exec error is
  `No such file or directory` for a binary that plainly exists, and the fix is a symlink for the
  missing interpreter rather than a rebuild or a patchelf; (2) "self-contained" covers the
  runtime and not the system ICU, and without it the process aborts at argument parsing with
  the reason only on stdout, so a container that stays up looks merely idle; (3) the bundled
  SDL dlopens its X11 dependencies at runtime, so `ldd` on it lists nothing useful and the
  X client libraries have to be declared by hand. A harness that vendors a tool build should
  record which of these three it has to satisfy, because none of them appear in the tool's own
  documentation as container concerns.
* **2026-10-23** — **A headless display is not a keyboard, and input has to be proven against
  emulator memory rather than against a screenshot.** In a container with no window manager,
  the usual way to focus a window fails outright, and with no focus set an injected key is
  swallowed silently: the send returns success and nothing moves. The durable rule is the
  verification, not the flag: confirm a key landed by reading a value the game is obliged to
  change (position, hit points) over the emulator's own API. A picture that did not change
  distinguishes nothing between a dead input path, a blocked move, and a screen that ignores
  input by design. This is the same trap the capture runbook already records for key
  injection, reached from the display side.
* **2026-10-23** — **Reference data that is a template rather than an instance makes a working
  container look broken, and the symptom points at the wrong component.** A pristine game
  backup includes the blank save the game uses for *creation*, which is not a loadable
  character; a container that mounts it unchanged boots, renders, accepts input, and then
  refuses to start a game. Any harness that mounts pristine reference material read-only should
  say explicitly which files are templates needing a seeded instance, and seed them from a
  writable location outside the reference tree.

* **2026-10-27** — **A reconstruction tree that numbers fragments in one space and labels
  them in another will generate phantom gaps, and the handoff document is where the
  contamination hides.** The clean asm tree names files by file offset and names body
  labels by a constant-biased second space (`label = file + 0x200`, the same bias the
  string extractor already used). A disassembler prints jump targets in the label space,
  so a note written from disassembly output mixes both: instruction addresses in one space,
  their targets in the other. One such note was read as "the target sits inside another
  fragment's span, grep-by-filename will not find it", and it became the declared blocker
  for a whole work item. The target file had existed all along; the number was off by the
  bias. The same slip had already propagated into a function header, where a `cmp` was
  attributed to the wrong routine because its cited address was a label read as a file
  offset. → Three rules. **(a)** A tree with two address spaces needs one named conversion,
  stated once, and every derived view must apply it — if the bias lives only in a constant
  inside one tool, it will not be applied by the next human or agent reading a note. **(b)**
  Before declaring an address a gap, apply every known bias to it and re-look; "no file
  begins here" is only evidence after the conversion has been tried. **(c)** Handoff and
  summary documents are the highest-risk place for this, because they quote addresses
  without the disassembly that produced them, and a downstream agent cannot re-derive the
  context. A blocker written as an address should carry its space.

* **2026-10-23** — **A hand-written analysis script is a derivation, not evidence, and it
  must be validated against the code it accuses before it is allowed to contradict prior
  measured work.** A script slicing a data file from the wrong base offset reported that a
  previously-measured record layout was impossible — "`hp` is zero in all 32 slots", "a
  field cannot be a shifted copy of another" — and every one of those structural
  impossibilities was an artefact of one constant in the script. The committed engine read
  the file correctly; the finding was fiction. It was committed, reported as a defect in the
  reconstruction, and used to block four downstream work items and compile out working code
  behind a guard, none of which was warranted. The engine's own `fread` was one file away
  and would have settled it in ten seconds. → Two rules. **(a)** When a new measurement
  contradicts a prior *measured* finding, the default hypothesis is the new one is wrong,
  and the cheapest test is to re-read the code path that consumes the same bytes. **(b)** A
  script producing a negative result needs a positive control pushed through the same code
  path in the same run — print something known-true with the same slicing, and if it does
  not come out true, the script is the bug. A table of numbers from an unvalidated
  derivation is the most dangerous artefact in a reverse-engineering pipeline, because it
  looks exactly like the real kind.

* **2026-10-23** — **A gate can report a metric that is structurally constant and still be
  green.** An acceptance runner printed its check count by grepping the child's output for a
  per-check success line — but the child's assertion macro prints only on failure, so the
  count was always zero. The exit code was checked, so the gate was not toothless; the defect
  was that the one number a reader trusts could never move, and a run that executed *zero*
  checks would have looked like the known cosmetic quirk. Two generic traps in the same
  file: a control model asserted to be "faithful" also passed on a zero-check build, because
  only its exit code was examined. → derive a reported count from the child's own summary
  line, assert it non-zero, and ship a self-test that *forces* a zero-check run and asserts
  the guard reads a real zero. A guard nobody can make fire is not a guard.

* **2026-10-23** — **Snapshot before the first mutating action, or your baseline is the

  state-observation protocol needs an explicit pre-touch snapshot step, and any claim of the

* **2026-10-23** — **A byte whose value fits a story is not evidence of that story.** A

  prints a location refusal — a gate about *where you are*, not what you own. The value
  coincidence was exactly what the flag would have been. → require a consumer that branches
  on the field before naming it, and when a name was assigned from a value match alone,

* **2026-10-23** — **Documented dead ends do not get read unless they sit where the work

* **2026-10-23** — **A string you treat as an error message may be the oracle.** A capture

  as "no response", read as a dropped input; the conclusion drawn was that the input path

* **2026-10-23** — An **emulator breakpoint is a one-way door, and "paused" is not proof

  "hit" may be the self-test's trap firing on an idle loop. Separately, the pause flag on
  the status endpoint is also set by ordinary memory reads, so a concurrent key-injection
  helper that verifies itself by reading memory produces real pauses at arbitrary
  addresses. A first version of the capture tool accepted "paused" as the breakpoint
  signal and reported a confident stop at the wrong address; the memory it printed was
  genuine, which is exactly what made it dangerous. A breakpoint harness must (a) assert
  the stop address equals the requested address and fail loudly otherwise, (b) treat a
  pause at any other address as noise to skip rather than a result, (c) never arm a
  self-test on an address the program will pass again, and (d) say so in its own output
  when it has made a run unusable. Breakpoints that cannot be removed mean **one emulator
  run per capture target**, an operational cost worth designing for up front.

* **2026-10-23** — **A fragment-splitting clean wave leaves the same wound everywhere, not
  only where it was noticed.** Once function boundaries were examined in one region, the
  identical pathology turned up in an unrelated one: a number-printing helper cut into five
  pieces across two call levels, each fragment ending on a branch into the next, none of
  them a routine. Reading any single fragment produced a plausible but wrong account, and
  the wrong account was internally consistent. After a mechanical boundary pass, run a
  detector for the shape instead of waiting to trip over it: a fragment whose only inbound
  edge is a fall-through from its immediate neighbour and whose tail branches forward into
  that neighbour is almost certainly one half of a split routine. Report candidates; do not
  merge them automatically, because a boundary is a claim about intent and the bytes only
  support the claim sometimes.

* **2026-10-23** — A **content guard must be expressed over content, not over files.** The
  asm-tree guard md5'd each changed file's non-comment lines against HEAD and failed on any
  deletion. That was correct while renaming was the only legal edit, and it silently became a
  blocker the first time function *boundaries* were allowed to move: merging fragments into
  routines deletes files by design, so the gate reported sanctioned maintenance as vandalism.
  The fix was to restate the invariant, not relax it — concatenate every file's non-comment
  lines in address order and compare the stream, which renames, merges and splits all preserve
  and which any body edit, insertion, deletion or reorder breaks. → any harness whose proof
  artefact is a set of named files should guard the **ordered content stream**, keyed on a
  semantic address rather than a path. Path-keyed guards encode an accident of packaging as a
  correctness property, and the first legitimate refactor discovers it. Restating was strictly
  stronger, not weaker: whole-file deletion is now caught by content loss and the first
  divergent line is named.

* **2026-10-23** — **A hand-written simulator of a target ISA needs a hand-computed case
  before it needs a conclusion.** A routine was modelled three times in one day and wrong
  twice: a shift-to-zero loop was read as a popcount, a swap-and-add sequence was read as a
  multiply, and the first simulator implemented decimal adjust by *subtracting* 6 instead of
  adding. Every version printed a confident number; the broken one produced a two-digit
  decimal result that looked like a plausible larger one, and nothing about it looked wrong. → a harness that derives behaviour by
  re-implementing target instructions in the host language must ship at least one
  hand-computed vector per emulated opcode, asserted in the same run, and must refuse to print
  a derived value when a vector fails. The same applies to the *reading*: a loop's exit
  condition and the order in which a register is read versus overwritten are the two places a
  confident misread concentrates, and both produce plausible output rather than an error.

* **2026-10-23** — A **truncated tool listing reads as an absent tool.** A remote
  emulator-control surface was queried with a response cap, four of sixty-three tools
  came back, and the screenshot capability appeared not to exist. The detour that
  followed — hand-decoding the framebuffer out of memory — produced a structured,
  plausible, *wrong* image, which is the dangerous shape: it looked like a partial
  success. → any harness that inspects a remote or paged surface must count what it was
  offered, compare against any declared total, and fail loudly on a mismatch. A partial
  list is worse than an exception. And a capability index is worth committing as a tool
  that prints the count, so the next session does not re-derive it.

* **2026-10-23** — A GUI emulator under X needs a **24-bit visual**, and 8-bit is the
  classic wrong answer precisely because it is the historically correct recipe for
  DOS-era pixel fidelity. It yields a blank screen with a completely happy log. →
  assert the visual depth at startup and refuse to start rather than debugging a blank
  window; the failure is silent and the obvious causes (display not exported, focus,
  timing) all look likelier than the real one.

* **2026-10-23** — **Score only what the source actually asserts.** A layout checker
  over shipped data files reported a clean pass in one sector and a total failure in
  another, and the failing sector's file simply *authored nothing* — so every populated
  runtime slot was being compared against a zero the file never claimed. The sector that
  had something to teach was the one being dismissed. → a conformance checker must
  restrict itself to entries the source declares, and must report "nothing asserted" as
  its own verdict rather than folding it into a mismatch count. Absence and contradiction
  are different findings and a scorer that conflates them produces confident nonsense.

* **2026-10-23** — **Never infer branch polarity from an idiom's name.** A
  decimal-adjusting subtract chain ends with a complement that inverts the carry, so the
  following "jump if below" fires on *success*, not on failure. Describing the routine by
  recognising the idiom produced a summary with the two branches swapped, and it survived
  review because the swapped version is also coherent — an affordable purchase and an
  refused one both make sense narratively. → when a flag decides a branch, simulate the
  flag through the exact instruction sequence over a few concrete operands and include
  the boundary cases (exactly enough, one short). It costs minutes and the error it
  prevents is invisible to reading.

* **2026-10-23** — **A filter tuned on one example silently drops a whole class.** An
  extractor was tightened to require a particular terminator; it removed the noise it was
  aimed at and also, without complaint, two of the records it existed to attribute —
  because multi-line records separate their lines with a *different* control byte, so the
  sample that was checked still looked correct. → when adding a filter, print the count
  before and after and assert that named known-good entries survive. A filter that only
  removes what you did not want is otherwise indistinguishable from one that removes what
  you did, and only the count tells you which.

* **2026-10-23** — **A negative result needs a planted positive.** A sweep that found no
  downward-oriented text anywhere in the shipped maps became trustworthy only after a
  synthetic map holding one was constructed and the sweep shown to detect it — and the
  classifier was then perturbed in two directions to confirm it could still go red.
  Without that control, "there are none" and "I could not find any" produce identical
  output. → every detector expected to report a negative must ship with a fixture that
  makes it report a positive, and the fixture belongs in the tool, not in a scratch dir.

* **2026-10-23** — **Engineer a disagreement instead of collecting more agreement.** Two
  candidate explanations for a rendered value were indistinguishable across a corpus where
  the two underlying fields agreed almost everywhere; more samples could not have settled
  it. One engineered exception — found by scanning the existing corpus for the *few* cases
  where the fields diverge, then reproducing one live — settled it with a single perfect
  observation. → when two hypotheses agree on nearly every sample, stop sampling and go
  look for the exceptions; a tool that reports disagreements first is worth more than one
  that reports match rates.

* **2026-10-22** — A string extractor that prints an address without its **owning
  function** invites a wrong story. Two similar catalogue strings sitting near each other
  were read as two variants of one thing and ticketed as a per-location difference; the
  owners turned out to be two unrelated routines serving two different player classes, and
  the difference was class, not location. Any harness that surfaces embedded strings should
  resolve each one to its function and show the function's name-evidence alongside, so a
  reader cannot describe a relationship between strings without also seeing that they live
  in different places. → cheap to build, and it is the difference between a string table
  and a claim.
* **2026-10-22** — Shipped data files can carry **leftover source text from the platform
  the game was ported from**, in the same records as real content. A dialogue extractor
  that assumes every record is displayable text will emit assembler mnemonics as NPC
  lines. Two guards worth building in from the start: never assume a fixed record stride
  (entry counts varied per file in the corpus that found this), and sample the tail of
  each file rather than only the head, because the stray bytes sit where the padding
  should be. Any harness that auto-generates a text decoder from one example file will
  encode the wrong structure. → see the data-inventory section of the owning
  implementation report.
* **2026-10-22** — A static finding identifies a site, not its reachability. A
  ticket was written to "fix" a clamping helper that turned out to have **zero
  callers** — dead code — while the live path beside it was already correct. Same
  root cause as the play/static limit: static analysis proves a line exists and
  what it does; it does not prove anything executes it. → any harness that generates
  candidate fixes must also report caller count, or the queue fills with confident
  non-bugs.
* **2026-10-22** — A cross-binary overlap probe can be built and fully calibrated
  without the second target in hand. A target pack's own unrelated executables give
  positive, patched-sibling and true-negative controls, and one of them is typically
  an MZ-headed non-DOS image — a free test of *refuse rather than guess*. Only the
  comparison waits for the second binary. → § 8 probe 1; split "build the tool" from
  "run the comparison" whenever a probe is blocked on external input.
* **2026-10-22** — A generic tool must be specified by what it may *not* depend on.
  Stating "no dependency on this target's function map, filename or address bias"
  is what stops a reusable tool quietly becoming a one-off. → § 4; add a
  *non-dependencies* clause to every harness component brief.

* **2026-10-22** — A negative table scan is a lead, not an answer. Searching a binary
  for a per-entity stat table and finding none is consistent with two very different
  shapes: the value is computed, *or* it is an immediate stored per case inside a
  dispatch chain -- which hand-coded and early-compiler binaries routinely do and which
  no table scan can find. The second shape was the real one here. → after a negative
  table scan, stop looking in the data and find the **store site**: locate the field in
  the action routine that decrements it, then walk backwards to the initialisers. The
  field is identified by what mutates it, not by where it lives.

* **2026-10-22** — Before hunting a stored table, test whether the numbers are a
  formula. A per-entity stat table is the obvious place to look for HP, and the obvious
  scan came back empty across every encoding and indexing tried -- which is only useful
  because the tool's threshold made a false positive impossible. The structure was in
  the numbers themselves: the values formed two arithmetic progressions, which says the
  quantity is *computed* and redirects the search from a data region to the routine that
  derives it. → commit the negative scan as a tool, not just the note; and run a
  progression check over any external stat table before scanning the binary for it.

* **2026-10-22** — A third-party wiki can name a tile, but only by bitmap identity.
  Community creature tables deliver a name and a bitmap in the same table cell, so an
  exact pixel comparison against the binary's own art table turns a crowd guess into a
  measured join — and incidentally exposes which community images are screenshot crops
  rather than rips. The join needs three guards to stay honest: reject any image with no
  integer path to the native tile size, reject a match that lands only on blank or solid
  tiles, and report a name claimed by two creatures as a conflict instead of picking one.
  → any harness that ingests external data must ship controls proving the matcher can
  answer *no*; a name sourced from outside the binary is a hypothesis the bytes get to
  veto.

* **2026-10-22** — A gate must be demonstrated failing before it is trusted passing.
  A CI script exited 0 unconditionally on the only branch ever taken, so it printed
  `FAIL` and reported `PASS` for a full checkpoint cycle. Found only by inverting an
  expectation to check the controls fired. → gate rule, Tier 2.
* **2026-10-22** — Controls must ship as fixtures, not live in scratch space. A
  discrimination proof written to `/var/tmp` was gone by morning and its numbers
  became an unfalsifiable claim. Rebuilt independently, both numbers reproduced
  exactly. → every gate ships its own positive and negative model.
* **2026-10-22** — Guard detection must know the ISA's idioms, not just the obvious
  mnemonics. A `cmp`/`test` search under-counted guards 3× because the real
  subtract idiom re-exposes the borrow via `cmc`. → Tier 1.
* **2026-10-22** — Packed-decimal field width *is* the ceiling, and the presence of a
  clamp is a mechanic. One play-observed instance generalised into a rule that
  predicted unobserved behaviour and confirmed an owner recollection. → Tier 1;
  strongest argument for the census-style generic decoder.
* **2026-10-22** — Game knowledge is fused into tool logic; the port cost is
  understated by any audit that greps for named constants. → drives § 4.
* **2026-10-22** — Deriving a value from evidence beats hardcoding it; the one tool
  that derives its segment is the only one that would have survived a rebuild of the
  target at a different load address. → § 4 design rule.
* **2026-10-25** — "String table rendered as machine code" is a detectable *class*, not a
  one-off. Two independent occurrences were found in one day by the same method: a span that
  decomposes entirely into printable runs separated by terminators, whose decoded "instructions"
  are all forced-keeps the assembler could not express. A harness should ship a detector for it
  rather than waiting for a human to notice a routine that never returns. The confirming check is
  arithmetic and target-independent: the entry starts must equal the running sums of the entry
  lengths plus terminators, which cannot hold by accident over a couple of hundred bytes. → Tier 1.
* **2026-10-25** — A reference scan for "is this region dead data?" gives **false negatives** when
  the data is reached through a stored cursor. Nothing loaded any entry address as an immediate and
  there was no offset table, so the obvious verdict was dead — and the region was live, reached by an
  address-take stored into a memory variable and walked by a selector that skips NULs to an index.
  A liveness detector that only greps for immediates will therefore delete load-bearing content, the
  worst possible direction for a gate to fail. It must also look for address-takes and for stores of
  them into memory. → Tier 1, and a standing warning for any "unused data" cleanup.
* **2026-10-25** — Typed trace fields break classifiers silently. Parsing an executed-instruction
  offset as a hex string when the dump stores a decimal number returns "never executed" for every
  address, including the ones that ran in every single capture. The classifier looked correct and
  produced a confident, uniformly negative answer. Any executed/not-executed gate must carry a
  positive control known to have run, and report it. This is the same shape as the lying tool in
  § 5, arrived at from the parser side instead of the detector side. → Tier 1.
* **2026-10-26** — An "execution trace" artifact can be a **deduplicated set**, and then every
  frequency question silently returns 1. The dump this project treats as the authority for "did
  this run" turned out to hold ~0.4% duplicates across 147 captures: perfect for *whether*, useless
  for *how many times*, and it answers a count query with a plausible `1` rather than an error. The
  tell was two unrelated captures sharing an identical entry count. A harness should record, per
  trace artifact, whether it is a trace or a set — and any classifier that needs a rate must say so
  and use a mechanism that can supply one. → Tier 1; same family as the lying tool in § 5, arrived
  at from the data-shape side.
* **2026-10-26** — A branch whose target is the block immediately after some *other* block is a
  **skip, not a guard.** Reading `cmp x,0 ; jne L` as "L is gated on x" is wrong when the
  fall-through path also lands on L; both arms reach it and the test only selects which intervening
  block runs. Getting this backwards was promoted into a header at `confidence: high`, implemented
  as a gate in the reimplementation, and produced a permanent-stuck state that only showed up when a
  person played the game. Checking the fall-through costs one disassembly and is the whole
  verification. → Tier 1, and an argument for never writing a branch's semantics without the
  surrounding layout.
* **2026-10-25** — A body-conservation guard that pairs old and new files **by filename** makes a
  clean rename pass or fail depending on commit granularity: alone it is conservation, alongside any
  marked body edit it is an unmarked change, because a rename is a removal plus an addition and only
  a marker attributes the pair. The guard's verdict was then also ref-dependent, which it had already
  been called out for once. Either pair by declared address, or make "rename in its own commit" a
  documented workflow rule — but do not leave it implicit, because the failure looks like vandalism
  reported against an innocent file. → Tier 2, gate design.

* **2026-11-05** — A **probe constant is a fixture, and letting a production path call the entry
  point that carries it turns a documented placeholder into a silently different starting state.**
  The engine had two ways into the world: one that spawns from the loaded save record, and one that
  spawns from a compile-time probe coordinate kept for dumps and screenshot comparisons. Its header
  said in as many words that the probe pair is "NOT an assertion about where a new game begins".
  A later feature routed a *real* entry — the shortcut that skips an obsolete disk-swap prompt after
  character creation — through the probe entry, and every new character then started in the wrong
  sector. It survived review for two weeks because the two paths are one function name apart at the
  call site (`run` versus `init_state`) and both return success. Three rules. Give a fixture entry
  point a name that cannot be typed by accident in a production call site, or make it take the
  record and fall back internally, so there is one door and no choice to get wrong. Second, when a
  feature "enters the world directly" it must enter the same world the load path enters, and the
  cheapest proof is a gate that asserts the resulting *position*, not that a command loop started —
  the existing test checked only that the world screen appeared, which was true in both versions.
  Third, and the reason this one was nearly missed: **the dumped state disagreed with the rendered
  frame**. The state still carried the record's sector while the view had been loaded from the
  probe's, so a dump-only check would have reported the correct location for a world that was not
  the one on screen. When an entry path can disagree with itself, assert on the field the renderer
  actually consumed, and read state *and* frame. → Tier 2, gate design.

* **2026-11-06** — **A palette index is a colour only inside one palette, so a renderer
  that hardcodes an index is correct on the table it was written against and silently
  erases content on any other.** The text layer is written in index 3 on index 0. A
  theme brought a 16-entry RGB table whose index 3 is a second black, so the ink was
  chosen from the palette at load and everything that read the frame's ink pair was
  fine — except one routine that repainted a single cell using the constants. That
  routine draws the text cursor, inverse video, so the symptom was not wrong colour
  but *nothing*: the block and the glyph under it were both painted in the
  background. Three rules. Any renderer path that picks a colour must take it from
  the frame or the palette in force, and a scan for the palette constants in a
  backend is a cheap review step. Second, when a defect produces "something is
  missing" rather than "something is the wrong colour", suspect a value that
  resolves to the background, because absence is what that looks like. Third, the
  gate has to read pixels: every text-level assertion passed, since the character
  grid was correct throughout and only the rendering of one cell was not. The cheap
  general check is a relational one that needs no colour names — here, the cell's
  modal colour must differ from the frame's background and be brighter — and the
  control must run under a second palette that was *never* broken, or a red control
  proves only that the check can fail. → Tier 2, rendering gates.

* **2026-11-06** — **Two entry points into one hardware seam must answer in the same
  alphabet, and a three-state return read as a two-state one turns a quit into the
  previous input.** The engine wrapped the original's single blocking key-read in two
  functions. One normalised its backend's `1 / 0 / -1` to `1 / 0`; the other returned
  the raw value. Every caller tested for the documented `0`, so the third state read as
  "input arrived", and the caller then consumed an output parameter the backend had
  deliberately not written. The symptom was not a crash and not a hang: it was the
  *previous keystroke, repeated* — the struct sat at the same stack offset on every
  iteration and still held what the last call had written through it, so a player
  pressing Ctrl-C on a form whose last key was Down saw Down. Four rules. (1) When two
  functions wrap one seam, diff their return contracts, not just their names; the
  asymmetry is the bug and it is invisible at every call site. (2) An out-parameter must
  say which return values write it, and a caller that reads it after any other value is
  reading uninitialised memory that will look like data. (3) Fix a three-state collapse
  at the seam, not at each caller — five sites had the same wrong test and a sixth would
  appear. (4) If a state can only be produced by one backend, no scripted test can reach
  it; write a fake backend that can say all three, gate the contract there, and record
  in the worklist which state stays unexercised in the shipped artifact. Separately, and
  it produced a false "still running" during verification: a job backgrounded by a
  non-interactive shell inherits SIGINT as ignored, so signal-handling tests need
  `setsid` or they measure the harness. → Tier 2, harness contract.

## 7. Non-goals and hazards

* **Not a second reconstruction.** The harness produces evidence and proofs; the
  conclusions still live in the target project's own tree.
* **Do not generalise from one sample without labelling it.** Every Tier 1 entry is
  "seen in one binary, expected to recur", not "verified universal".
* **Over-abstraction is a real risk.** A profile schema designed before a second
  target exists will encode this game's shape and call it generic. Build the
  *minimum* profile that lets the existing tools run unchanged here, then let
  target two break it — that is the honest test of the abstraction.
* **Contamination.** This document is method only. If a line here only makes sense
  for one binary, it belongs in that project's findings doc, not here.

## 8. Next probes, in order

1. **Measure the engine-overlap claim instead of assuming it.** Extract function
   byte-bodies from both DOS binaries, normalise, hash, intersect. A large
   intersection means shared lineage and changes the whole plan; a near-empty one
   means the transfer is method-only. Cheap, offline, and it settles the question
   before any budget is spent on the reuse assumption.
   **Status 2026-10-22: tool queued, comparison blocked.** The probe needs a second
   game, which is owner-supplied input. The *tool* does not — a target pack normally
   ships several unrelated executables, and those supply a full calibration set:
   self-comparison, a patched sibling of the same program (which tests normalisation
   rather than length), an unrelated binary as a true negative, and — usefully — at
   least one file that carries an MZ header but is not a DOS image at all, which
   tests whether the tool refuses instead of printing a confident number. Design
   lesson: **build and calibrate the generic tool against the current pack; only the
   comparison waits for the second target.**
2. **Extract the profile from this project without changing behaviour.** The
   refactor is done when every existing tool and gate still passes against
   `profiles/<this game>.json`. That is a mechanical, verifiable first step and it
   proves the schema is sufficient.
3. **Only then** instantiate a second profile, and expect it to break the schema.

**Calibration on target choice.** A same-era, same-author port is the best case and
may share code. A same-era DOS game shares the ISA tier. A later protected-mode,
compiler-generated title shares almost nothing at Tier 1 — no real-mode segment
arithmetic, no BCD counter fields, different video — and would take Tier 2 method
only. Expect the transfer value to decay fast with era and platform.

**A synthetic input file is a cheaper discriminator than a second real one.** When a runtime value
could have come from the file on disk or from the program writing its own constant, the obvious move
is to find another real file where the two differ — which usually means reaching a different part of
the game, which usually means a level transition, a teleport, or a save edit that may not be honoured
and will silently leave you measuring the sector you started in. If the harness can install a
generated file under the same name before launch, overwrite the field in question with a value the
program could never have produced and watch which one survives. One boot answers it, and the answer
is about the program rather than about that one file. Prefer this whenever the value is per-file and
the file is replaceable.

**A mechanical call-site transcription must model writes the callee makes to shared state.**
The usual shape of a hand-written drawing or I/O routine in this era is a small number of
zero-page variables holding a parameter block, called repeatedly with only some of the fields
reloaded each time. A generator that reads the caller and emits one assignment per field the
caller writes looks exactly right and is wrong whenever the callee also writes those fields —
which subroutines that walk a line, scan a string, or advance a cursor routinely do, because
incrementing the parameter in place is cheaper than copying it back. The symptom is not a
crash and not a missing output: it is geometry or text that is present, plausible, and
displaced, which is the worst class of defect to find by looking at a picture. Two rules follow.
First, when transcribing a call site, read the callee for stores to the same addresses the
caller loads, and carry them. Second, when a shape routine reloads only a subset of the fields
before a call, treat that as evidence the rest are live state and ask what last wrote them —
a routine that reloads nothing between calls is a state machine, not a list of independent
draws.
